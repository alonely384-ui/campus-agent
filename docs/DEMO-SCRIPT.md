# 附录一：导师/评委可能问什么（按官方评分维度归类）

## a. 技术深度

| 问题 | 回答 |
|---|---|
| 和直接传 PDF 给 ChatGPT 有什么区别？ | 那个是黑盒，没法保证它给的页码是真的；我们是自建检索链路，页码可点回去核对，拒答也可控 |
| 为什么不用 LangChain 这类框架？ | 框架会把中间过程藏起来，某步出错时说不清是哪步。手写能保证每层都能解释、能单测 |
| 三路召回的权重怎么定的？ | 不用权重，用倒数排名融合 RRF（k=60）—— 三路分数尺度不同，直接加权不可比，融合只看名次 |
| 为什么引用降权放在重排之后？ | 重排看语义相关性，被引密集的段落天然像"相关"，先降权会被重排覆盖；放后面才真正生效 |
| 五个角色算真多智能体吗？ | **严格说不算。**是单推理循环里的五个显式阶段，角色间走共享上下文而非消息总线。真多智能体要每角色独立调模型互发消息，一次问答会从 6 秒涨到一两分钟，演示直接超时。**但角色间唯一真正有状态转移的交互 —— Verifier 打回 Retriever —— 是真实实现并测过的** |
| **Function Calling 你做了什么？** | 标准 OpenAI 工具协议：schema 注册表 → `tool_choice="auto"` → 解析 `tool_calls` → 逐个执行 → 以 `role="tool"` + `tool_call_id` 回填 → 最多 5 轮。计算工具用 AST 白名单，不做 eval |

# 附录二：AI 协同贡献与 Prompt 调优策略

> 官方说明 3.4 要求参赛选手在技术文档中说明 AI 的协同贡献与 Prompt 调优策略。以下是本项目的如实记录，可直接用于答辩。

## AI 用在哪、不用在哪

| 环节 | 是否用 AI 辅助编程 | 说明 |
|---|---|---|
| 解析、检索、图谱、写作的**结构设计** | 否 | RRF、交叉编码器重排、PageRank、Brandes 中介中心性、Louvain 的选型与参数由人工确定，AI 只做实现 |
| 代码实现与重构 | 是 | 大量样板代码（FastAPI 路由、数据模型、测试骨架）由 AI 生成后人工逐条审阅 |
| 缺陷定位 | 是 | 例如 `docs_dense` 删除失败被 `except Exception: pass` 静默吞掉、`RAG_RERANK` 推导的属性名对不上真实变量 —— 人工发现现象，AI 辅助定位到行 |
| 技术文档与讲稿 | 是 | 由 AI 起草，**所有数字必须跑命令实测后再写进去**（见下文「数字的取证方式」），禁止凭印象 |

## Prompt 调优策略（四条）

1. **约束写成结构，不写成祈使句**
   「请勿编造参考文献」是无效的 —— 模型不认为自己在编造。真正有效的是**移除能力**：候选池编号 + 强制 `[C3]` 标记 + 参考文献由代码生成。提示词只负责讲清「标记的含义」，不负责保证真实性。

2. **只给数据，不给图**
   生成图表 Caption 时只把**统计摘要**（最大值、最小值、趋势方向、量级跨度）喂给模型，不传图片。实测生成的 Caption 里每个数字都能在摘要里对上 —— 因为模型手上根本没有别的数字。

3. **拒答写在 System Prompt 最前面**
   「资料不足时明确说明」放在开头几条，而不是结尾补一句。位置越靠前权重越高。

4. **按角色分提示词，方向不同就完全另写**
   中译英（`app/zh2en.py`）和英译中（`app/translate.py`）是两个完全独立的 Prompt，不是同一个加个方向参数。中译英七条硬规则：只输出译文 / 正式学术语域禁缩写 / 术语一致 / 长句拆短 / 数字单位引用标记与 LaTeX 原样保留 / 时态规矩 / 不增不减。分块翻译时把上一块末尾 400 字作为上下文传递，保证术语连贯。

## 数字的取证方式（这条最重要）

本项目所有对外数字遵守一条规则：**说出口之前必须先跑一条能吐出这个数的命令**。踩过的坑：早期文档写「364 个测试」，那是带过滤的跑分，实际是 481；写「12,548 行」，实际是 14982。现在这些数字全部由 `scripts/` 下的取证脚本产出，随文档一起更新。
