## 模块 0 · 先建立一张全景图

在钻细节之前，先记住一句话：

> **这个项目所有的设计，都在解决同一个问题——「怎么让大模型说的话，每一句都能被查到出处」。**

这句话就是官方赛题评分里「抗幻觉 RAG 与源头溯源 8%」的那 8 分。展开来是三条防线：

| 防线 | 在哪里 | 做了什么 |
|---|---|---|
| 检索准 | `app/rag/pipeline.py` | 三路召回 + 交叉编码器重排，保证"该找到的段落一定在候选里" |
| 引用实 | `app/agent.py` | 证据卡片带着文件名和页码，模型不许凭空说 |
| 生成限 | `app/writing.py` | 写作助手只能引用候选池里的编号，参考文献由代码生成，模型碰不到 |

后面四个模块，就是这三条防线的拆解。

## 模块 1 · RAG 检索链路（最重要的地基）

### 1.1 先搞懂 RAG 到底在干嘛

最朴素的做法是：把论文全文塞给模型，让它自己找。这条路走不通，因为有两个硬限制：

1. **上下文放不下**。39 篇论文，平均每篇 20 页，全塞进去几十万 token，费用和延迟都爆。
2. **放得下也找不准**。材料太长时模型会「中间迷失」——首尾看得清，中间一整段直接忽略。

RAG（Retrieval-Augmented Generation，检索增强生成）的思路是：**先检索出最可能包含答案的几段原文，只把这几段交给模型，并要求它指着这段话回答。**

于是整个系统的质量，从「模型聪不聪明」变成了「你检索得准不准」。这就是为什么这一块占了最多的代码。

### 1.2 为什么要三路召回，而不是一路

代码：`app/rag/pipeline.py:879 retrieve_scored()`

一路召回的问题在于，**没有哪种检索方式在所有问题上都强**：

| 检索方式 | 擅长 | 死在什么问题上 |
|---|---|---|
| 哈希向量（`pipeline.py:916`） | 零依赖、离线兜底，任何环境都能跑 | 精确度最低，只适合当备胎 |
| 稠密向量（`pipeline.py:925`，ONNX MiniLM） | 问法和原文用词不同也能匹配（"并行度" ↔ "parallelizable"） | 专有名词、数字、缩写容易糊掉——它比的是"意思像不像" |
| BM25 关键词（`pipeline.py:933`） | 精确定位专有名词、数字、公式符号 | 换个说法就找不到——它比的是"字面上有没有这个词" |

举一个具体例子：问「Transformer 用了多少块 GPU 训练」。稠密向量会把整段讲"训练效率"的文字都召回来（语义像），但真正含答案的那句「we trained on 8 NVIDIA P100 GPUs for 12 hours」里的 `P100` 和 `8`，只有 BM25 能精确命中。

**所以两个通道是互补关系，不是替代关系。** 这也是赛题 1.2 里"多篇知识问答"能撑住的原因：换了篇论文，两路各有一半机会先捞到正确段落。

> **如果只做一路会怎样？** 只做稠密：数字题、专有名词题几乎必错。只做 BM25：学生换个说法提问（中文问英文库）就崩。这不是"准确率低一点"的问题，是"某一类问题直接归零"的问题。

### 1.3 三路结果怎么合成一个排序：RRF

三路各自给出一个排名，但**它们的分数不能直接相加**——稠密给的是余弦相似度（0~1），BM25 给的是无上界的词频分，哈希向量又是另一种量纲。硬加在一起就是拿米和斤相加。

解决办法是 **RRF（Reciprocal Rank Fusion，倒数排名融合）**，代码在 `app/rag/pipeline.py:864`：

```python
fused[cid] = fused.get(cid, 0.0) + weight / (_RRF_K + rank + 1)
```

翻译成人话：**只看名次，不看分数**。某一路里排第 1 的块得 `1/(60+0+1)`，排第 10 的得 `1/(60+10+1)`。同一块被多路同时召回，分数就累加。

为什么 `_RRF_K = 60`（`pipeline.py:190`）？这个常数的作用是**抹平头部名次的差距**。K 越小，第 1 名和第 2 名的差距越大，融合结果越倾向于"某一路的绝对第一名"；K 越大，各路名次差距被压平，融合结果越倾向于"被多路共同认可的块"。60 是文献里的常见默认值，也是小库场景下比较稳的取值。

三路权重在 `pipeline.py:185-187`：`dense=2.0 / bm25=1.0 / hash=0.5`。稠密权重最高，因为它在语义类问题上确实最强；哈希最低，只当兜底。

> **加分细节**：`pipeline.py:859-860` 有个降级逻辑——如果稠密通道挂了（`dense_ids` 为空），哈希通道**自动接管**稠密的 2.0 权重。这不是随手写的，是为了「换个没装好模型的环境，检索不至于整体失效」。

### 1.4 为什么召回完还要再重排一次

到这里候选池里已经有 50 个块（`_RECALL_DEPTH = 50`，`pipeline.py:199`）。但"在候选里"不等于"排第一"。

`app/rag/rerank.py:1-28` 的模块注释把这件事讲得很清楚：

- **召回用的是双塔（bi-encoder）**：问题和文档**分别**编码成向量，再算余弦相似度。优点是文档向量可以离线预计算、检索快；缺点是「问题和文档从没在同一个模型里见过面」，细粒度关系表达不出来。
- **重排用的是交叉编码器（cross-encoder）**：把「问题 + 文档」拼成一个序列**一起**送进模型，每一层注意力都能看到两边的词。所以它能把"数字、否定、限定词"这些细粒度关系判出来。

代价是慢：每个候选都得现算一遍。所以只拿前 15 个去重排（`_RERANK_POOL = 15`，`pipeline.py:196`），不是拿全库。

> **为什么是 15 不是 50？** 代码注释里写了实测：pool 取 10/15/20 时 R@1 分别是 28/31/30（38 题测试集）。15 和 20 差 1 个，在噪声范围内，但候选少 1/4，省时间。**这是在"质量不吃亏"的前提下选的最小代价点。**

### 1.5 核心问题：融合分和重排分为什么不能混

这是我自己踩过的一个真 bug，也是最值得讲的一个点。

**现象**：证据卡片上出现了「融合分 **-0.0777**」。分数怎么可能是负的？

**根因**：`app/rag/rerank.py:127-128`

```python
for (chunk, _old_score, channels), score in ranked[:top_k]:
    out.append((chunk, score, [*channels, "rerank"]))
```

重排之后，**RRF 融合分被交叉编码器的原始 logit 直接覆盖了**。而 logit 是可正可负的实数（`rerank.py:19-21` 的注释原话：「onnx 输出的是 logits（可正可负的实数），不是 0~1 的概率；它只在同一批候选内部有意义」），负数完全正常——`tests/test_rerank.py:46` 里就写死了 `score=-4.07` 当测试用例。

**问题出在前端**：`web/index.html` 原来把分数标签写死成「融合分」，从来不读后端给的 `score_type` 字段。而后端 `app/agent.py:1135` **早就**给了：

```python
"score_type": "rerank" if "rerank" in self.channels else "rrf",
```

**修法**：前端按 `score_type` 分别显示「融合分」和「重排分」，并加 tooltip 说明「交叉编码器打分，只在同一批候选内可比」。

**为什么这个点重要**：这两个数字的**语义完全不同**。
- 融合分（RRF）反映的是"在几路榜单里排第几"，恒为正，但**不是概率，不能说"0.8 就是 80% 正确"**。
- 重排分（logit）反映的是"交叉编码器认为这段话多相关"，可正可负，**只在同一批候选内部可比**。

把它们混成一个叫「相关度」的数字给用户看，等于告诉用户一个假信息。这在论文工具里是很严重的问题——**用户会拿这个分数去判断要不要读这篇论文**。

> 顺带一提：`web/guide.html:516` 的讲解文字里早就写着「rrf 和 rerank 分数不可比，前端要分开显示」。**文档说对了，代码没做到**——这也是个可以讲的教训：设计文档和实现之间会脱节，需要检查。

### 1.6 引用怎么溯源到页码

三件事：

1. **切块时就带上页码**。`pipeline.py:46-53` 的 `Chunk` 数据结构里就有 `page` 字段。
2. **证据卡片直连阅读器**。`Evidence.to_dict()`（`app/agent.py:1129-1138`）输出 `source`（文件名）+ `page` + `text`，前端拼成 `reader.html?paper=xxx.pdf&page=2`，点击直接跳到原文那一页。
3. **Verifier 角色做自检**。`app/agent.py:1025-1034`：

```python
pages_known = sum(1 for ev in evidence if ev.page is not None)
if not evidence:
    verdict, ok = "没有检索到任何证据，回答会明确说明资料不足", False
elif pages_known == 0:
    verdict, ok = f"证据 {len(evidence)} 条但都缺页码，引用无法溯源", False
else:
    verdict, ok = f"证据 {len(evidence)} 条，其中 {pages_known} 条可定位到具体页码", True
```

**为什么只做这三种判定，不做"置信度打分"？** 注释里写了理由（`agent.py:1023-1024`）：「这里只做能自动判定的部分，不做主观打分——判不准就不判，宁可说'有证据'也不瞎给置信度」。让模型给自己打 0.87 分，那 0.87 是编的。

### 1.7 顺手讲两个真实调参

- **切块大小 300 字**（`pipeline.py:66`）。注释里的实测：120/150/200/300 的检索命中率在 150 之后就不再提升（top3 都是 3/3），但 300 的块数只有 150 的一半（180 vs 334）。所以选 300：**质量一样，成本减半**。
- **参考文献片段降权 0.6**（`pipeline.py:209`，`_looks_like_citation`）。参考文献条目形如 "Author et al. Title. arXiv:2312.14925" 也在索引里，容易抢到 top1。处理方式是**降权不硬删**（`pipeline.py:986-989`），保留可追溯性。注意降权放在重排**之后**，否则重排名次会把惩罚覆盖掉。

### 1.8 模拟追问

**Q1：你怎么证明三路召回比一路好？**

回答思路：先承认「我没有做过严格的消融实验，但有三条间接证据」。①代码里保留了环境变量 `RAG_W_DENSE / RAG_W_BM25 / RAG_W_HASH`（`pipeline.py:183-187`），本来就是为消融准备的；②容错设计能证明它们是互补的不是重复的——`pipeline.py:887-888` 注释写「哪一路挂了就跳过这一路，其余通道继续融合」，如果三路等价，挂一路直接就没法用了；③具体到"Transformer 用了多少 GPU"这类数字题，只有 BM25 能精确匹配 `P100`，这是原理上可推的。

**更诚实的说法**：「3 路是不是最优组合我没验证，但这三路的失效场景是互补的，只留一路会让某一类问题直接归零。」

**Q2：RRF 的 k=60 是怎么定的？**

回答：文献常见默认值 60。代码注释（`pipeline.py:188-189`）写了它的作用：k 越大名次差距被抹得越平，k 越小头部名次越吃重。库里只有 39 篇论文、块数量不大，属于"短查询、小库"，实际调到 20–30 可能更好，但我没做这个实验。**承认没做，比编一个理由安全。**

**Q3：融合分 0.5 是不是表示 50% 可能正确？**

回答：不是。RRF 分只反映"在几路榜单里排第几"，恒为正，无上界，不是概率。真正带有"相关性强度"含义的是重排分（logit），但那个也只是批内相对值。所以我前端的标签写的是「融合分」和「重排分」，不是「相关度」。

**Q4：重排为什么只取前 15 个？取全部不会更准吗？**

回答：会更准一点，但代价不成比例。实测 pool=10/15/20 时 R@1 是 28/31/30，15→20 只涨 1 个，在噪声内，但要多算 33% 的候选。而且第一次召回的深度只有 50，重排池再大也超不过 50，收益很快见顶。

**Q5：如果模型给出的答案没有引用任何证据，你怎么发现？**

回答：分两层。①Verifier 角色会把「证据 N 条 / 可定位页码 M 条」回显出来，如果 `ok=False` 前端显示红点；②系统提示词里明确要求「如果以上片段没有能回答问题的内容，直接回答：论文库中没有找到相关信息」（`app/agent.py:1004`）。实测问「Attention 的核心机制是什么」时，模型主动说了「检索片段只给出零散描述，没有 attention 的形式化定义…资料不足」，没有编造。

## 模块 2 · 1.5 引用关系图谱

### 2.1 先讲清楚「图」在这里是什么

一句话：**把库里 39 篇论文当作点，把「A 引用了 B」当作边，画成一张网。**

有了这张网，能做四件单篇论文做不了的事（正好对应赛题 1.5 的四小项）：

| 赛题 | 问题 | 这张网怎么回答 |
|---|---|---|
| 1.5.1 引用图谱 | 这些论文之间什么关系 | 可视化 + 社区划分 |
| 1.5.2 基石节点 | 哪几篇是整个领域的根 | PageRank / 入度 / 中介中心性 |
| 1.5.3 自动综述 | 这个领域在讲什么 | 按社区 + 年份 + 关键词归纳 |
| 1.5.4 前沿探索 | 接下来该看什么 | 近两年被引 + 跨社区桥接 + 未被接入 |

### 2.2 第一个坑：先把副本合成一个点

探路时的实测数据（只读脚本，跑完删了）：库里 **39 个 PDF**，参考文献条目 3149 条，但建图前发现 `1706.03762`（Attention Is All You Need）在库里有 **4 份**（`1706.03762v7.pdf`、`1706.03762v1.pdf`、`1706.03762v7.pdf`、`1706.03762v1_img.pdf`），另有一个文件名是哈希 `bdfaa68d8984.pdf` 的也是它。

**如果不合并会发生什么？**
- Attention 的「被引次数」会被拆成三份，每份都变少，看起来这篇论文不重要；
- 它的 PageRank 也被稀释，因为链接分散到三个节点；
- 图上出现几个标题一模一样的点，看起来像 bug。

**怎么合并的**：`app/graph.py` 的 `build_nodes()`（`:967`）产出 `LogicalNode`（`graph.py:85-96`），一个逻辑节点持有 `copies: list[str]`（多个 PDF 文件名），`canonical_id` 按 `arxiv:1706.03762` 这种形式生成（`_canonical_id`，`graph.py:154`）。**不删文件**，只在图里合并。

合并后：**39 个文件 → 36 个逻辑节点，并掉 3 个**。

> 这里有个可以讲的设计取向：**合并逻辑和数据分离**。原 PDF 一个不动，`data/papers/` 里还是 39 个文件，阅读器照样能打开任意一份；只是"图"这个视图里把它们看成同一个点。这样既不破坏已有功能，又能让指标正确。

### 2.3 第二个坑：怎么判断「参考文献里的这条」就是「库里的某篇论文」

这是整个 1.5 里最难的工程问题。参考文献条目长这样：

```
[1] Ashish Vaswani, Noam Shazeer, Niki Parmar, et al. Attention is all you need.
    In Advances in Neural Information Processing Systems, pages 5998–6008, 2017.
```

你要从这个字符串里判断：库里有没有这篇论文？有三层证据，优先级从高到低（`app/graph.py:1028 match_references()`）：

**第 1 层：arXiv 编号**（`graph.py:1078-1086`）

```python
if ref.arxiv_id and ref.arxiv_id in by_arxiv:
    dst = by_arxiv[ref.arxiv_id]
    method, score = "arxiv", 1.0
```

最硬。但**覆盖率很低**——探路实测：3149 条被引条目里，arXiv ID 只出现 **22 次**。原因很实际：很多论文写的是会议名（NIPS、ACL），不写 arXiv 号；而且写法五花八门（`arXiv:1706.03762` / `1706.03762v2` / 全角冒号）。

所以只靠 arXiv 号建不出图，**标题匹配才是主力**。

**第 2 层：完整规范化标题 + 词袋校验**（`graph.py:1092-1100`）

```python
cand = by_title.get(_fuzzy_key(ref.title))
if cand is not None and node_bags[cand.canonical_id] == _title_bag(ref.title):
    dst = cand
    method, score = "title_exact", 1.0
```

这里是**我自己踩过的坑**。原来的写法是「把标题去掉所有空格和标点后比字符串相等」（`norm_title`，`graph.py:100-113`）。看起来没问题，但：

`A Survey of Large Language Models` → `asurveyoflargelanguagemodels`
`Survey of Large Language Models` → `surveyoflargelanguagemodels`

只差个首字母 a。库里如果同时有 `A Survey of X` 和 `Survey of Y`，去空格后很容易撞上。

**修法**：加上第二道校验——**词袋（词的多重集合）必须完全相等**（`_title_bag`，`graph.py:144`）。`A Survey of...` 的词袋是 `{a, survey, of, large, ...}`，`Survey of...` 少了 `a`，词袋不等，不连边。

> 注意 `norm_title` 的 docstring（`graph.py:103-105`）特别强调：**不截断**。截断会让 `Attention Is All You Need` 和 `Attention Is All You Need For Video` 变成同一个 key——这是另一个方向的错。

**第 3 层：标题近似匹配**（`graph.py:1102-1130`）

用 `difflib.SequenceMatcher` 算相似度，然后按两个阈值分流：

```python
if best_node is not None and best_score >= fuzzy_accept:   # 0.92
    dst = best_node; method = "title_fuzzy"
elif best_node is not None and best_score >= fuzzy_review: # 0.75
    reviews.append({...})   # 只记待人工核验，不出边
```

阈值定义在 `graph.py:44/46`：`FUZZY_ACCEPT = 0.92`、`FUZZY_REVIEW = 0.75`，都可以用环境变量 `GRAPH_FUZZY_ACCEPT` / `GRAPH_FUZZY_REVIEW` 覆盖。

**为什么 0.75~0.92 之间不出边，而是进「待人工核验」列表？**

这是**溯源系统的核心取向**：宁可少一条边，也不要一条假边。因为一张引用图的全部价值在于"这是真的引用关系"。如果混进 30% 的假边，那这张图从"证据"降级成了"猜测"，用户就没法拿它做判断了。所以中间地带不猜，**如实标出来"这两条我觉得像但不确定，你自己看"**。前端有一个专门的「低置信度匹配（待人工核验）」区域展示这个列表。

> 这不只是工程洁癖。赛题评分里「抗幻觉 RAG 与源头溯源 8%」——**承认不确定，本身就是抗幻觉的一部分**。

**还有一个自引陷阱**（`graph.py:1061-1101`）：参考文献里可能引用这篇论文自己（综述、勘误常见）。如果不拦住，第 2 层会精确命中源节点本身，然后在写边时被静默丢弃，接着掉进第 3 层模糊匹配，撞上库里另一篇标题相近的论文——**凭空造出一条边**。所以代码里用 `self_hit` 显式判定「键相同 + 词袋相同」就记 `self_reference` 跳过。

### 2.4 三个指标必须分开：被引次数到底指什么

这是用户明确要求、也是评委最容易抓的点。

| 字段 | 含义 | 代码位置 |
|---|---|---|
| `citation_edge_count` | 这个节点**引用**了库内几篇（出度） | `graph.py:1238` |
| `cited_by_count` | 这个节点**被**库内几篇引用（入度） | `graph.py:1239` |
| `pagerank` | 被有影响力的论文引用才算数（间接影响力） | `graph.py:1240` |

汇总层还有三个不同的数（`graph.py:1250-1255`）：

```python
"file_count": len(rows),                                  # 合并前：PDF 文件数 = 39
"node_count": len(node_payload),                          # 合并后：逻辑节点数 = 36
"edge_count": len(edges),                                 # 引用边数 = 189
"cited_paper_count": len({e.target for e in edges}),      # 被引用论文数（去重）
"citing_paper_count": len({e.source for e in edges}),     # 不同引用论文数（去重）
```

**「引用边数量」和「被引论文数量」为什么不是一回事？** 因为一篇论文可能被引用 5 次，产生 5 条边，但被引论文数只算 1。用 Attention 举例：它被库内多篇引用，`cited_by_count` 是个位数，但它参与了很多条边。

**为什么这个区分重要？** 如果汇报时说「共有 189 次引用」，评委问「那被引最多的论文被引几次」，你答不上来就露馅了。正确说法是：「**189 条引用边，覆盖 N 篇被引论文，来自 M 篇不同引用者**」。

### 2.5 PageRank 在说什么：为什么它比"被引次数"多一层信息

**直觉理解**：PageRank 的原始含义是"一个网页重要，是因为重要的网页链向它"。换成论文就是：**一篇论文重要，是因为重要的论文引用了它。**

代码在 `app/graph.py:1156-1174`，标准实现：

```python
for _ in range(rounds):
    for nid in node_ids:
        score = (1 - damping) / n             # 传进来的"基础分"
        for src in in_links.get(nid, []):     # 每一篇引用它的论文
            score += damping * rank[src] / max(1, out_deg[src])   # 贡献自己分数的一部分
        updated[nid] = score
```

`damping = 0.85`：85% 的权重来自引用者，15% 平均分配给所有节点（防止"没有任何入边"的孤立节点分数归零）。

**关键在 `rank[src] / out_deg[src]` 这个除法**：一篇论文的"影响力"要**平均分给它引用的所有论文**。所以：
- 被 BERT 引用 = 光荣（BERT 分高）；但如果 BERT 引用了 50 篇，那这 50 篇平摊，每篇分到的不多。
- 被一篇只引用 3 篇的论文引用 = 分到的更多。

**这就是 PageRank 相对"被引次数"的增量信息**：被引次数只看数量，PageRank 还看**引用者的质量**和**引用者的挑剔程度**。

**具体例子**：`Layer Normalization` 这篇，被引次数不算最高，但在库里 PageRank 顶级。为什么？因为它是 Transformer 的组成部分，被那些高 PageRank 的论文引用。它的影响力是**间接的、基础件式**的——没人会说"我的方法基于 Layer Norm"，但所有 Transformer 变体都在用它。所以代码里给它单独的角色标签 `foundation`（`graph.py:1349-1353`）。

> 这个例子特别适合在答辩时讲：**它说明"被引次数"这个最常见的指标会漏掉基础设施类工作，而 PageRank 能捞回来。**

### 2.6 基石节点是怎么算的：为什么不做"取 Top-10"

代码在 `app/graph.py:1300-1359`（`cornerstone_scores`）。

三个指标，各自先压成 0~1 的**分位**，再加权：

```python
score = 0.45 * ind_pct[i] + 0.40 * pr_pct[i] + 0.15 * bc_pct[i]
```

- `ind_pct`（0.45）**入度分位**：被多少篇库内论文直接引用——"直接影响力"
- `pr_pct`（0.40）**PageRank 分位**：被有影响力的论文引用才算数——"间接影响力"
- `bc_pct`（0.15）**中介中心性分位**：连接不同子领域的那类论文——"桥接作用"

**为什么必须先转成"分位"再相加？** PageRank 的取值范围是 0~0.2，被引篇数是 0~20，中介中心性另一套量纲。直接相加的话 PageRank 那一项会被完全淹没（0.05 + 18 和 0.06 + 18 没区别）。代码注释（`graph.py:1275-1277`）写得很直白：「不先统一量纲就没法加权」。

**为什么用分位而不是 min-max 归一化？** min-max 是 `(x - min) / (max - min)`，单个极端值会把其余所有点压扁。分位只看"排第几"，规模无关，更稳。

**为什么不做「取 Top-N」？** 注释原话（`graph.py:1309-1310`）：「库里只有 36 个节点，硬截断会把比邻的节点判错。改成给连续分数 + 角色标签，前端按分数降序，阈值可调。」——36 个点里取 Top-5 和取 Top-6 可能就差 0.001 分，硬切会让一个本该上榜的论文掉出去。**给连续分 + 标签，让人自己判断**，这是同一套哲学。

**角色标签**（`graph.py:1341-1355`）：

| 标签 | 条件 | 含义 |
|---|---|---|
| `cornerstone` | 入度分位 ≥0.75 **且** 桥接分位 ≥0.75 | 真基石：又稳又被引，还串起不同方向 |
| `hub` | 入度分位 ≥0.75 | 被大量引用，但只在自家社区里 |
| `bridge` | 桥接分位 ≥0.75 | 穿针引线，连接两个原本不相连的社区 |
| `foundation` | PageRank 分位 ≥0.90 但入度桥度都普通 | 通用基础件，影响力是"间接"的 |
| `fringe` | 其他 | 边缘：没怎么被库内引用 |

> 为什么要有 `foundation` 这个标签？代码注释说得很实在：如果 Layer Normalization 直接判 `fringe`，会和前端「N 条金边 = PageRank 前 3」的事实**自相矛盾**——图上它是金边，列表里它说自己是边缘。**内部一致性**是这种多视图系统必须照顾的。

### 2.7 中介中心性：不用 networkx 自己写

代码在 `app/graph.py:1362-1408`，用的是 Brandes 1992 算法（`graph.py:1386` 注释标了出处）。

**直觉**：如果从 A 到 B 的最短路径都必须经过 C，那 C 就是 A 和 B 之间的"桥"。数一遍所有点对的最短路，看有多少条经过它。

**为什么不用 networkx？** 注释（`graph.py:1365-1366`）写得很清楚：「自己用 BFS 数最短路，不依赖 networkx / scipy——库里 scipy 没装，`nx.pagerank` 会直接 ModuleNotFoundError，所以整条链路只用标准库。」

这其实是个**部署决策**：多一个依赖就多一份"别人克隆下来装不上"的风险。而且这个算法本身不复杂（BFS + 一次反向累加），自己写 40 行可控。

> **加分点**：`requirements.txt` 里 networkx 被我删掉了——AST 扫全库 `import` 确认代码根本不用它。依赖清单和代码一致，这本身就是工程质量（`scripts/check_deps.py` 在 CI 里做自动比对）。

### 2.8 模拟追问

**Q1：39 篇论文的图，能说明什么学术价值？**

回答：规模确实小，我承认。但 1.5 要的不是"复现一个引用网络分析平台"，而是**把方法跑通并且每个结论可核对**。39 篇是赛题测试数据的量级，方法换成 3 万篇是一样的（`match_references` 是线性扫描，瓶颈在 PDF 解析）。而且我有一个真实发现：Attention 在库里是 4 个副本，如果不做副本归并，它的被引数和 PageRank 都会被拆成三份——**这说明三步匹配和副本归正是必需的，不是装饰**。

**Q2：PageRank 在小图上不可靠吧？**

回答：对，38 个节点时 PageRank 的分辨率有限，这也是我不拿它单独下结论的原因。所以我做了三层：①它只是基石分的一部分（权重 0.40，入度 0.45，桥接 0.15）；②基石分给的是连续分数 + 角色标签，不是"取 Top-N"硬截断；③每个标签旁边都有 `pagerank_pct / cited_pct / bridge_pct` 三个分位可查，用户可以自己判断。**PageRank 单独看确实容易误导，和入度、桥接一起看就稳了。**

**Q3：参考文献解析错了怎么办？**

回答：三层匹配里有明确的"不猜"地带。相似度 0.75~0.92 之间的不连边，进「待人工核验」列表，前端单独一栏展示，写明「相似度落在阈值之间，没有计入图谱，避免误连」。实测这个列表有 48 条。另外每条边都记了 `match_method`（arxiv / title_exact / title_fuzzy）和 `match_score`，图上悬停能看到「匹配方式：title_exact」——**任何一条边都可以被追溯到"凭什么连上"**。

**Q4：为什么 0.92？为什么不是 0.9 或 0.95？**

诚实回答：0.92 和 0.75 是我根据"标题相似但不同论文"和"同一论文不同写法"的实际样本调的，不是从某篇论文抄的。0.9 会多放过一些边界情况，0.95 会漏掉真实匹配。更好的做法是拿一批人工标注的对子做 ROC 曲线定阈值，但我没做。**这两个阈值可以用环境变量改，就是留给这件事的位置。**

## 模块 3 · 多智能体四角色 + FastAPI 工程架构

### 3.1 从一句提问到一段回答：完整链路

先在脑子里跑一遍"问一个问题"的全过程：

```
浏览器 web/index.html 输入问题
   ↓  fetch POST /chat/stream（SSE）
FastAPI app/main.py:165 chat_stream()
   ↓  调 run_agent_stream()
app/agent.py:1369
   ↓  第一步：_rag_context_with_evidence()  ← 四个角色在这里跑完
   │    ├─ Planner    ：把中文问题换成英文检索词
   │    ├─ Retriever  ：三路召回 + 重排（模块 1 讲的全在这）
   │    ├─ Extractor  ：加工结构化材料（精华卡 / 表格行 / 章节页）
   │    └─ Verifier   ：自检证据够不够、能不能溯源
   ↓  yield {"type":"evidence", "items":[...]}   ← 证据卡片先发出去
   ↓  yield {"type":"roles", "items":[...]}      ← 时间线也先发出去
   ↓  第二步：进入 LLM 多轮循环（最多 MAX_ROUNDS 轮）
   │    ├─ 模型决定直接答 → {"type":"answer_delta", ...} 逐字吐
   │    └─ 模型要调工具 → 执行 → 结果塞回对话 → 下一轮
   ↓  yield {"type":"done"}
浏览器收到 SSE 事件流，边收边渲染
```

**为什么用 SSE 而不是普通 HTTP？** 因为一次问答要 6~20 秒。普通 HTTP 意味着用户盯着转圈 20 秒，什么都看不到。SSE（Server-Sent Events）允许服务端一条一条推，前端一边显示「正在检索…」一边等。`app/main.py:187-197` 那个 `StreamingResponse` 里有个关键 header：

```python
# ⚠️ 这一行很重要！不加的话 Nginx 会把流缓冲起来，
#    前端就变成"等半天然后一次性全出来"，流式效果全没了。
"X-Accel-Buffering": "no",
```

这条在生产环境踩过坑的人才会写——不加它，本地测试好好的，一上线流式就失效。

### 3.2 四角色：为什么要做，又是怎么做的

**背景**：官方赛题 AI 技术深度 35% 的原文里点名了「多智能体协同」。我原本的系统是**单 Agent + Function Calling**，没有明确角色。

**面临两个选择**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 真多智能体 | 四个独立的 LLM 实例，互相传消息讨论 | 一问多调 3~4 次 LLM，演示从 20 秒涨到 2 分钟 |
| B. 显式命名既有阶段 | 把本来就在跑的四个阶段命名、各留可核验产物 | 零额外 LLM 调用，但"协同"是编排层的，不是模型层的 |

**我选了 B**。理由写在 `app/agent.py:1070-1074` 的注释里：

```python
# 四个角色：官方赛题「AI 技术深度」点名要「多智能体协同」。
# 这里的做法不是让四个模型互相聊天（那样一个问答要多调 3~4 次 LLM，
# 演示时会从 20 秒涨到 2 分钟），而是把本来就在跑的四个阶段显式命名、
# 各自留下可核验的产物，让用户能看见"谁做了什么"。
# 好处：调用次数不变，但每一步都可追溯、可截图、可单独测试。
```

**这是一个可以坦率讲出来的取舍，而且讲出来就是加分项**——因为**我明确知道代价是什么**（"协同"的强度弱于真正的多 Agent 讨论），也知道在什么条件下会换方案（如果 LLM 延迟能压到 2 秒以内，或者比赛允许更长响应时间）。

### 3.3 四个角色各干什么

数据结构是 `RoleRun`（`app/agent.py:1091-1111`）：

```python
@dataclass
class RoleRun:
    role: str            # planner / retriever / extractor / verifier / writer
    summary: str         # 给人看的一句话，前端时间线直接显示
    duration_ms: int = 0 # 耗时
    detail: dict = ...   # 结构化补充
    ok: bool = True      # 这一步成功没有
```

| 角色 | 干什么 | 代码 | 实际输出例子 |
|---|---|---|---|
| **Planner 规划** | 中文问题换英文检索词；判断单篇/多篇/全库 | `agent.py:677-685` | 「全库检索 · 检索词「core mechanism of attention」」 |
| **Retriever 检索** | 三路召回 + 重排 | `agent.py:719-730` | 「召回 4 段原文，覆盖 2 篇论文」 |
| **Extractor 抽取** | 把原文加工成模型能直接用的材料 | `agent.py:1011-1022` | 「本次问题不需要结构化加工，直接用检索片段」 |
| **Verifier 校验** | 自检证据够不够、能否溯源 | `agent.py:1035-1043` | 「证据 4 条，其中 4 条可定位到具体页码」 |
| **Writer 写作** | 调 LLM 生成答案 | `agent.py:1282-1289` | 「生成答案（912 字，第 1 轮定稿）」 |

**几个设计细节值得讲**：

1. **Planner 为什么只做"换检索词"这种小事，不做一个复杂的规划器？**
   因为库是英文论文、用户问中文，字面和向量都对不上——这是**唯一必须做的一步**。做更复杂的规划（比如把问题拆成子问题）会多调一次 LLM，收益不确定。

2. **Extractor 什么时候"不需要加工"？**
   判断条件是 `ev.channels[0] in ("card", "table-rows", "table", "section")`（`agent.py:1009`）。如果检索到的是普通正文段落，就不加工；如果是表格行、精华卡、章节页，才加工。**如实报告"没做"，比假装做了更有说服力**。

3. **没有证据时，时间线不能停在 Retriever**（`agent.py:749-768`）。
   ```python
   # 即使没检索到，也要把 Extractor/Verifier 写进时间线：
   # 否则界面停在 Retriever，"为什么没答案"就无从解释。
   ```
   这是个很细的可用性问题：如果时间线只有 2 个角色，用户会以为是系统卡了；补上「没有召回任何片段」和「回答会明确说明资料不足」（红色），用户就知道是**知识库里真的没有**，而不是系统坏了。

### 3.4 状态回显：一句话说清"这一问到底用了多少材料"

`_make_status()`（`app/agent.py:1153-1171`）产出形如：

```
证据=4 · 覆盖论文=2 · 页码=2,11
```

设计参考了 paper-qa 的 `Status: Paper Count=12 | Relevant Papers=5 | Current Evidence=8 | Current Cost=$0.0021`——**用一行字把"你凭什么这么答"摆出来**。

三个细节：
- 页码只显示前 8 个，多的用 `…`（`agent.py:1164-1166`），否则一行放不下；
- 写作轮次 > 1 时才追加「写作轮次=N」（`agent.py:1167-1170`），说明模型为了回答问题调了工具；
- 没有证据时直接返回「证据=0 · 本轮按资料不足作答」（`agent.py:1158-1159`）——**这句话本身就是承诺**。

### 3.5 前端怎么渲染的

`web/index.html` 里加了 `renderRoles(botEl, items, status)`：一个白底卡片，标题「多智能体协作」+ 绿色状态条，下面是竖排的角色时间线，每个角色一个小圆点（失败时变红）+ 名称 + 一句话 + 耗时（右对齐，等宽数字）。

DOM 顺序是**时间线在上、证据卡片在下**——先告诉你"我怎么找的"，再给你"找到了什么"。实测验证：`roles_bottom: 1093 ≤ evidence_top: 1101, order_ok: True`。

### 3.6 FastAPI 那几条值得讲的设计

**① 异常不泄漏到前端**（`app/main.py:146-149`）

```python
except Exception as e:
    logger.exception("处理 /chat 失败")
    # 不要把原始异常直接抛给用户（可能泄漏内部信息），记日志 + 返回通用提示
    raise HTTPException(status_code=500, detail="服务器处理失败，请稍后重试") from e
```

**② SSE 用 FastAPI 原生 StreamingResponse**（`app/main.py:187`），不需要 `sse-starlette` 这个额外依赖。这也是我后来从 `requirements.txt` 里删掉那个包的原因——用不到的一律删。

**③ 33 个接口按赛题编号组织**。`app/main.py` 里每个路由的 `summary` 都标了对应赛题：

```python
@app.get("/graph", summary="论文引用关系图谱（读缓存，1.5.1 / 1.5.2）")
@app.get("/writing/renderers", summary="本机可用的架构图渲染器（1.6.2）")
```

好处是**评委打开 `/docs`（FastAPI 自动生成的接口文档）就能一条条对照赛题验收**。

**④ 懒加载 + 缓存**。重排模型（23MB ONNX）不是启动时加载，而是第一次用到才加载（`app/rag/rerank.py:53-58` 的 `_load()`）。理由：服务启动快，而且如果用不到重排（环境变量关掉）就完全不加载。

### 3.7 模拟追问

**Q1：你这算多智能体吗？四个角色不就是一个流程的四个函数？**

最诚实也最有力的答法：**不算严格意义上的多智能体，是"角色显式化的单 Agent 编排"**。真正的多智能体意味着多个模型实例各自有记忆、自主决策、互相协商——MA-RAG 那类工作里 Planner 和 Extractor 是两个独立的 LLM。我这个版本里四个阶段是代码编排的顺序流程，只有 Writer 真正调了 LLM。

**但我选择这么做的理由是可辩护的**：①一问多调 3~4 次 LLM，演示时响应从 20 秒涨到 2 分钟，体验直接崩；②四个阶段的**边界**和真正的多智能体是一样的（规划、检索、抽取、校验、写作），升级路径清晰；③现在每一步都有可核验产物（`RoleRun` 的 summary + detail + duration），这是真多智能体也必须有的东西。

**Q2：为什么不把 Extractor 做成一个独立模型？**

两个原因。一是延迟；二是**当前 Extractor 做的事（挑出卡片、表格行、章节页）本质是规则，不是判断**——用 LLM 做只会更慢更不稳。什么时候该升级成模型？当需要"判断这段话是否支持结论"这种真正的语义判断时。

**Q3：Verifier 凭什么说"证据够"？它没有真的验证。**

对，这个 Verifier **只做能自动判定的部分**：证据条数、有没有页码。它**不做**"这几条证据是否真的支持答案"的判断——那需要 LLM 再看一遍，成本高且不可靠。

我在代码注释里明确写了这个边界（`agent.py:1023-1024`）。**一个诚实的弱 Verifier 比一个假装强的 Verifier 好**：如果它给个 0.87 的置信度，用户会以为那是真的概率。

**Q4：SSE 断线了怎么办？**

目前没做自动重连，前端用的是 `fetch` + `ReadableStream` 手动解析（不是 `EventSource`）。如果服务端异常，会 `yield {"type":"error","message":"服务器处理失败"}`（`main.py:182-185`），前端显示错误。**这是已知局限**——真要上生产，需要加"会话可恢复"，工作量不小，这个比赛场景下优先级不高。

**Q5：为什么不用 LangChain？**

这是我被问过最多的问题。理由：①这个项目的检索链路（RRF 权重、参考文献降权、页码溯源、容错降级）都是定制逻辑，套框架反而要跟框架的抽象打架；②LangChain 版本迭代快，依赖体积大，和一个"别人克隆下来要能跑起来"的项目目标冲突；③整条链路自己写的好处是**每一行都能解释**——被追问时能翻到具体代码，而不是"框架内部实现的"。

## 模块 4 · 1.6 写作助手

### 4.1 核心问题：怎么让模型"无法编造"参考文献

这是 1.6.1 框架生成的全部意义。

**普通做法**（也是大多数人用 ChatGPT 写论文的方法）：直接让模型「写一篇关于 X 的引言，带参考文献」。结果必然是**编造**——模型会生成看起来极其像真的引用，作者、年份、期刊全对，但那篇论文根本不存在。这叫 hallucinated citation，是学术写作里最致命的问题。

**我的做法：候选集约束生成**。核心思路是——**不给模型编造的机会，因为在结构上它拿不到写参考文献的权力。**

流程（`app/writing.py:249-300` `generate_framework()`）：

```
1. 用 idea 检索真实文献 → 得到候选池，每篇分配一个 key（C1, C2, ...）
   ↓  pool = lit.build_candidates(queries, total_limit=16)      writing.py:268
2. 候选池整个塞进 prompt，明确要求"只能引用池内编号"
   ↓  messages = build_framework_prompt(idea, pool)             writing.py:282
3. 模型写正文，引用只写 [C3] 这种标记，不写完整条目
   ↓  markdown = await chat(messages, temperature=0.4)          writing.py:283
4. 代码从 markdown 里抓出所有 [Cn] 标记，逐个校验是否在池内
   ↓  check = check_citations(markdown, pool)                   writing.py:285
5. 参考文献列表由代码根据 cited_keys 从候选池真实元数据生成
   ↓  references = build_reference_list(check.cited_keys, pool) writing.py:286
```

**关键在最后两步**。`format_reference()`（`app/writing.py:168-187`）的 docstring 第一句就是：

> **`**只有这里能产生条目**`**

模型的输出里**根本没有参考文献条目的字符串**，条目是 `format_reference` 从 `Candidate` 对象（真实检索结果的元数据）里拼的。模型想编也只能编出一个 `[C99]`，而 `[C99]` 不在池里，会被 `check_citations` 抓出来放进 `unknown_keys`。

**所以「出现不存在的论文」在结构上不可能**——不是因为提示词写得严，而是因为**生成条目这件事根本不在模型的能力范围内**。

### 4.2 三层防护的具体实现

| 层 | 手段 | 代码 |
|---|---|---|
| 事前 | 候选池整个注入 + 明令「只能引用这些编号」 | `writing.py:80-104` `FRAMEWORK_SYSTEM` |
| 事中 | 模型只能写 `[C3]`，不能写完整条目 | 同上，第四节 References：「**只写你用到的编号列表**」 |
| 事后 | 抓出所有标记，池外的进 `unknown_keys` 暴露 | `writing.py:138` `check_citations` |

`CitationCheck`（`writing.py:125-135`）有三个字段：
- `cited_keys`：引用到的、池内的
- `unknown_keys`：引用到但池里没有的（**这就是编造**）
- `unused_candidates`：池里有但没被引用的

`ok` 属性的定义是 `not self.unknown_keys`。**注意：`unknown_keys` 不会被悄悄删掉**（`writing.py:141-142` 注释：「这是我们要暴露出来的问题，不能悄悄删掉当作没发生」）——前端会标红。

**还有一个更细的坑我修过**：`_MARK_GROUP_RE`（`writing.py:47-49`）原来的写法会导致 `[C2, C3]` 这种组合引用**只取到 C2**，C3 被静默丢弃。修法是在一个正则里用组捕获整串，再 `re.split(r"[,;，、]", group)` 逐个取。

**空池时不硬生成**（`writing.py:270-280`）：

```python
if not pool:
    return {..., "warning": "没有检索到任何真实文献，为避免编造引用，未生成框架。请换个更具体的 idea。"}
```

**这条比任何提示词都重要**：检索不到东西的时候，正确做法是**不生成**，而不是让模型自由发挥。

### 4.3 一个真 bug：作者全是「作者信息缺失」

**现象**：生成出来的参考文献，每一篇的作者都是「作者信息缺失」。

**排查链**：
1. `data/catalog.json` 39 条记录，字段是 `['file','title','authors_count','pages','arxiv_id','year','category',...]`——**只有 `authors_count` 这个计数字段，没有作者名单**。`sum(1 for c in cat if c.get('authors'))` = **0/39**。
2. 但 `data/meta/structures.json` 里 **38/39** 有 `authors`，比如 `1607.06450v1.pdf -> ['Jimmy Lei Ba', 'Jamie Ryan Kiros', 'Geoffrey E. Hinton']`。
3. 问题在 `app/literature.py` 的 `search_local`：构造 `Candidate` 时**没传 `authors`**。而 `Candidate` 定义（`literature.py:73`）第 82 行明明有 `authors: list[str] = field(default_factory=list)`。

**修法**：新增 `load_local_authors()` 读 structures.json，按 PDF 文件名索引作者名单，在 `search_local` 里带上。

**顺手修的第二个 bug**：`et al.` 和 `n.d.` 自带句点，直接拼 `.` 会变成 `et al..`。修法（`writing.py:186-187`）：

```python
cleaned = [p.rstrip(". ") for p in parts if p]
return ". ".join(cleaned) + "."
```

**为什么截断到 6 位作者**（`MAX_REF_AUTHORS = 6`，`writing.py:52`）？T5 有 12 位作者、RWKV 十几位，全列出来一条参考文献占三行，既不像论文也不便读。IEEE 用 6，跟它对齐。

> **这个 bug 的价值**：它说明了「数据源 architecture」的重要性——同一个信息在 catalog.json 和 structures.json 两个地方，一个有名单一个只有计数，而代码读错了那个。**这类问题不看真实输出是发现不了的。**

### 4.4 1.6.2 架构图：为什么选这三个渲染器

赛题要求"生成架构图"。可选方案和取舍（`app/diagram.py:3-17` 的模块注释已经把这段写好了）：

| 工具 | 优势 | 劣势 | 做没做 |
|---|---|---|---|
| **Mermaid** | 语法最接近自然语言，模型基本不写错 | 默认出图偏"网页味"，圆角+彩色，进论文要调主题 | ✅ 做了 |
| **Graphviz** | 出的图最像学术论文的下图（黑白、方框、正交边） | 需要系统装 graphviz | ✅ 做了 |
| **TikZ** | 论文模板最正宗（IEEE/ACM 直接支持） | 模型写 TikZ 语法错误率高，一步失败就整段重来 | ✅ 后来补上了（带兜底） |
| **PlantUML** | 生态成熟 | 需要 Java 运行时装 JAR，多一层依赖 | ❌ 不做 |

**TikZ 一开始我故意没开放**，注释原话（`diagram.py:16-17`）：「真要上，得先加"编译失败自动重试"的兜底，否则现场演示一次红字就崩了」。

**后来怎么补的**：三层兜底（`diagram.py:145-195` `render_tikz`）：
1. 本机没装 `pdflatex` → 直接返回可读错误（`renderer_available()` 会提前告知前端，把选项灰掉）
2. 编译失败 → 从日志里抠第一条 `! ` 开头的错误行回报
3. PDF 转 PNG 失败 → 返回可读错误

而且 **preamble 是固定的**（`TIKZ_PREAMBLE`，`diagram.py:95`）：`\documentclass[border=6pt]{standalone}` + `tikz` + `ctex` + 几个常用库。这样模型只需要写 `\begin{tikzpicture}...\end{tikzpicture}` 这段，**出错范围被压到最小**。模型要是写了 `\documentclass` 也原样保留（`build_tikz_source`，`diagram.py:104`），不双重包裹。

**渲染失败的重试策略**（`diagram.py:460-480`）：

```python
# 只让模型改语法，不允许改结构，避免它"修着修着把图改成别的"
fix_msgs = messages + [
    {"role": "assistant", "content": raw},
    {"role": "user", "content": f"这段代码渲染报错了：\n{err[:800]}\n\n请只修正语法错误，**不要改变图的语义和结构**，重新输出完整代码。"},
]
```

**只重试一次**。注释写了理由：「不做无限重试——既浪费额度，又可能让模型越改越偏」。还失败就返回「渲染失败 + 原始代码 + 错误信息」，让人自己改——**而不是只给一个红字报错**。

**两个 Windows 上的真坑（很好的答辩素材）**：
- **`shutil.which` 不能用**：Windows 的 `PATHEXT` 里 `.CMD` 排在 `.EXE` 前面，而 `%APPDATA%\npm\mmdc` 还有个无扩展名的 Git Bash 脚本，`shutil.which` 会先命中它，然后报 `OSError: [WinError 193] %1 不是有效的 Win32 应用程序`。所以自己按 `.cmd → .exe → .bat → 无后缀` 顺序找（`_which`，`diagram.py:61`）。
- **Graphviz 中文变豆腐块**：默认字体 Times-Roman 不含 CJK 字形，中文节点全渲染成方框。修法 `_ensure_font`（`diagram.py:337-359`）在 `digraph {` 后注入 `graph/node/edge [fontname="Microsoft YaHei"]`。要是代码里已经指定了 fontname 就原样返回，不覆盖。

### 4.5 1.6.3 数据可视化：两个真取舍

**取舍一：为什么用两条渲染路径**

| 路径 | 用途 | 技术 |
|---|---|---|
| 网页预览 | 交互（悬停看数值、切换图例） | ECharts，前端 JS |
| 投稿导出 | 静态 PNG，直接放进论文 | matplotlib，服务端 |

理由：**它们服务的论文流程不同环节**。写作阶段要"边改表边看图"，交互图方便；定稿阶段要"贴进 LaTeX 的一张图"，必须是静态文件。一套代码做两件事反而都不精。

**取舍二：三维雷达图为什么网页端是假的**

赛题原文是「折线图、柱状图或三维雷达图**等**」。三维雷达图上不做真 3D 的原因（`chart.py:334-340` 注释）：

> 网页用本地 echarts 标准版，不含 GL，画不出真 3D；而投稿用的静态图用 matplotlib 的 mplot3d 就能出一张真的立体图，两处各司其职。

实测确认：本地 `web/vendor/echarts/echarts.min.js`（1,030,855 字节）**没有** `bar3D` / `radar3D` / `echarts-gl`。走 CDN 加载 echarts-gl 的话断网就白屏——演示环境断网，这个风险不能冒。

所以：**网页端出三角雷达（`radar3d` 分支，`chart.py:235`），导出端出真 3D 散点（`_export_radar3d`，`chart.py:334`）**。同一个 `radar3d` 图型，两条路各自给出自己能做的最好版本。

> 注意：网页端「三维雷达」如果数据不足 3 列，会**自动退化成普通雷达图**——宁可少一维，也不能因为缺列直接报错。

**自动选图型的逻辑**（`choose_chart`，`chart.py:110-155`）也踩过坑：

原本的逻辑是「有 3 个数值列 + 没有类别列 → 选雷达图」。结果 CSV 里是 `params, accuracy, loss` 这种数据时选成了雷达图——**参数越多精度越高，本质是自变量-因变量关系，散点才有意义**。

修法（`chart.py:124-141`）：先找「严格单调递增/递减且唯一值占比 > 0.8」的列当自变量（x 轴），剩下的当因变量。如果找不到这种列，才考虑雷达图。

```python
uniq_ratio = s.nunique() / max(len(s), 1)
monotonic = s.is_monotonic_increasing or s.is_monotonic_decreasing
if monotonic and uniq_ratio > 0.8:
    axis_col = c
    break
```

**还有个必须讲的对数轴判断**（`_needs_log`，`chart.py:314-331`）：

```python
return hi / lo >= 100
```

为什么是 100 倍？注释（`chart.py:317-320`）：「参数量 0.34B 到 540B 是 1600 倍，线性轴上小的几个点会挤在原点附近完全看不出差别；而准确率 86-93 这种不跨数量级的数据用对数轴反而会误导读者。」

**这是个非常有说服力的例子**：同一个"要不要用对数轴"的判断，用错了在两个方向上都是错的——该用的地方不用，小模型全挤在原点；不该用的地方用了，会把 86→93 的微小差异放大成陡峭曲线。

**Caption 只给统计摘要，不给图**（`write_caption`，`chart.py:502`）。理由：**避免模型描述出图上不存在的趋势**。给它的只有 `profile()` 算出来的真实数字（min/max/相关系数），它只能基于真数字写。实测生成的 caption：`Accuracy ranges narrowly from 86.7 to 93.1 across a roughly 1,600-fold span in parameter count, with a moderate positive correlation (r = 0.70).`——**每个数字都来自统计摘要，没有编造**。

### 4.6 模拟追问

**Q1：候选集约束生成会不会让模型写得很死板？**

会，而且这是**有意接受的代价**。模型只能用 16 篇候选文献，如果你的 idea 恰好不在这些论文的覆盖范围内，Related Work 会写得勉强。

但这个代价换来的是「参考文献 100% 真实」。在学术写作场景里，这个交换比是值得的——一篇引用假的 Related Work 比一篇引用少的 Related Work 危险得多。

**而且有个数据支持**：实测 `unknown_keys=[]`（模型一次都没编造编号），12 篇候选被引用了 12 篇（`unused=[]`），说明候选池的检索质量够用，模型不需要编造。

**Q2：为什么不干脆让模型写完整参考文献，然后我人工核对一遍？**

因为**人核对不可靠**。编造的参考文献看起来极其像真的——作者是真实的研究者、期刊是真实存在的、年份合理。除了去 Google Scholar 逐条搜，没有别的办法识别。39 篇全人工核对就是 39 次搜索。

我的做法是把「核对」这件事**变成结构上不需要**：模型从来没碰过条目字符串，条目是从真实检索结果的元数据拼的。

**Q3：ECharts 是你们自己开发的吗？**

不是，是开源可视化库。它的作用是把我们算好的数据点画成图。真正属于我们的部分是：自动选图型的规则（`choose_chart`）、对数轴的判断门槛（`_needs_log`）、雷达图逐列归一化、以及"标题/坐标轴/caption 的数字必须来自统计摘要"这一整套约束。

**Q4：TikZ 渲染失败率有多高？**

我没有系统测过失败率。实测生成 RAG 架构图时一次成功，但这不能说明什么。所以我做了三层兜底，**目标不是"保证成功"，而是"失败的时候不崩、给可操作的信息"**。

**Q5：写作助手生成的内容，学术上能用吗？**

只能当**骨架**用，不是终稿。它的定位在 `FRAMEWORK_SYSTEM` 里写死了：「帮助研究者从零起草论文框架」。Abstract 150-220 词、Introduction 3-5 段、Related Work 按脉络归类——这些是**结构建议 + 真实文献定位**，写什么、怎么论证还是研究者自己决定。

这一点我在 README 的「创新点」里也写明了：**候选集约束的收益是"不编造"，不是"写得好"**。

### 五句话讲清五个"为什么"

1. **为什么三路召回？** 因为它们失效场景互补——稠密管语义，BM25 管精确词，哈希当离线兜底。只留一路，某一类问题直接归零。

2. **为什么融合分和重排分要分开显示？** RRF 分反映名次、恒为正、不是概率；重排 logit 可正可负、只在批内可比。混成一个"相关度"等于给用户假信息。

3. **为什么 0.75~0.92 之间不出边？** 溯源系统的价值在于"引用是真的"。宁可少一条边，也不要一条假边——中间地带进「待人工核验」列表，如实标出来让人自己判断。

4. **为什么四个角色不让它们互相聊天？** 一问多调 3~4 次 LLM，演示响应从 20 秒涨到 2 分钟。把既有阶段显式命名、各留可核验产物，调用次数不变但每步可追溯。

5. **为什么写作助手的参考文献不可能编造？** 因为生成条目这件事根本不在模型的能力范围内——它只能写 `[C3]`，条目由 `format_reference` 从真实检索元数据拼。

### 三个"我不确定"（准备好被问）

被问到这些，**直接承认，不要编**：

1. **三路召回是不是最优组合？** 没做严格消融实验。代码里留了环境变量（`RAG_W_DENSE` 等）为它准备着。
2. **0.92 / 0.75 这两个阈值怎么定的？** 按实际样本调的，不是抄论文的。更好的做法是人工标注一批对子做 ROC 曲线，没做。
3. **四角色算不算多智能体？** 不算严格意义的多智能体，是"角色显式化的单 Agent 编排"。真多智能体需要独立模型实例互相协商，那个版本延迟不可接受。
