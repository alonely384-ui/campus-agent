## 一、先看硬约束：我的项目要多少资源

这些数字是**本机实测**出来的，不是估的。

### 1.1 内存占用（用 psutil 测整个进程树）

| 状态 | RSS 占用 |
|---|---|
| 刚启动，只加载 FastAPI | **205 MB** |
| 加载引用图（189 边） | 210 MB |
| 计算 Louvain + 中介中心性 | 211 MB |
| **跑一次完整问答（召回 + ONNX 重排 + LLM）** | **876 MB** |

跑一次问答涨了 **665 MB**，主要是 ONNX Runtime 加载重排模型（22 MB 的 model.onnx，展开到内存后 200-300 MB）加上 chromadb 把 26596 条向量读进内存。

### 1.2 磁盘占用

| 目录 | 大小 |
|---|---|
| `data/chroma`（向量索引，26596 条） | **299.1 MB** |
| `data/papers`（39 篇 PDF） | 129.7 MB |
| `data/models`（重排模型） | 22.7 MB |
| `data/meta`（结构/图谱 JSON） | 4.4 MB |
| 代码 + 前端 | 5.3 MB |
| **合计** | **约 457 MB** |

### 1.3 结论：2G 内存画不出来

- 空闲 205 MB 看着还好，但**跑一次问答直接冲到 876 MB**
- Linux 系统本身要吃掉 200-300 MB
- 2G 配置只剩 1.7G 给应用，碰上并发（评委同时点）或重排模型加载，**极易 OOM 被杀**
- **必须 2核4G 起**

## 四、部署时要注意的三件事

### 4.1 磁盘怎么处理

代码仓库里**不含** 457 MB 的数据（`.dockerignore` 和 `.gitignore` 都排除了 `data/papers`、`data/chroma`）。三种做法：

| 做法 | 说明 | 推荐度 |
|---|---|---|
| **打包上传** | 本地压缩 `data/` 后 scp 上去解压 | ✅ 最省事，数据固定不变 |
| 服务器上重建索引 | 传 PDF，跑 `scripts/build_index.py` | 🟡 慢，但要装 OCR 依赖 |
| 挂对象存储 | 复杂，不划算 | ❌ |

### 4.2 重排模型必须一起传

`data/models/ms-marco-MiniLM-L-6-v2/`（22.7 MB）**必须上传**，否则 `app/rag/rerank.py:64-66` 会抛 `RerankUnavailable`，检索质量降级到纯 RRF。

### 4.3 用 systemd 让它常驻

别用 `nohup`，断线就死。写个 `research-assistant.service`：

```ini
[Unit]
Description=campus-agent
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/campus-agent
ExecStart=/opt/campus-agent/.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000
Restart=always
RestartSec=5
MemoryMax=3G

[Install]
WantedBy=multi-user.target
```

`MemoryMax=3G` 是保险丝——内存超了先杀进程重启，好过整机卡死。

## 五、验收标准

部署完成后必须验证这几条：

```bash
# 1. 健康检查
curl http://<IP>:8000/health
# 期望：{"status":"ok","model":"deepseek-chat","version":"0.1.0"}

# 2. 问一次完整问题（这条最吃内存，必测）
curl -X POST http://<IP>:8000/chat -H "Content-Type: application/json" \
     -d '{"message":"Attention 的核心机制是什么？"}'
# 期望：HTTP 200，返回带证据卡片的答案

# 3. 看内存有没有爆
free -h

# 4. 浏览器打开前端
http://<IP>:8000/ui/
```
